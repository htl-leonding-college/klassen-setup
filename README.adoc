Einheitliche Arbeitsumgebung fuer den Unterricht — Ubuntu 26.04 LTS oder macOS.
Zwei Scripts mit verschiedenen Aufgaben:

[cols="1,3",options="header"]
|===
|Script |Aufgabe

|`setup-tools.sh`
|Werkzeuge installieren. Idempotent, unbeaufsichtigt, beliebig oft wiederholbar.

|`setup-identity.sh`
|Name, E-Mail, SSH-Schluessel, GitHub-Anmeldung. Einmalig und interaktiv.

|`versions.env`
|Die verwendeten Versionen — die eine Stelle, an der sie stehen.
|===

== Einstieg

Bewusst *kein* `curl … | bash`. Ein fremdes Script ungelesen mit erhoehten
Rechten auszufuehren ist genau die Gewohnheit, die ihr euch nicht antrainieren
sollt. Der Umweg ist der Lehrinhalt.

NOTE: Eine Ausnahme gibt es, und sie wird benannt statt versteckt: SDKMAN
bietet keinen Paketweg an. `setup-tools.sh` laedt dessen Installer deshalb
herunter, legt ihn als `.cache/sdkman-install.sh` ab, nennt Pfad und Groesse
und fuehrt ihn erst dann aus. Die Datei bleibt liegen und ist nachlesbar — das
ist der Unterschied zu einer Pipe.

[source,bash]
----
# 1. Herunterladen
git clone https://github.com/htl-leonding-college/klassen-setup.git
cd klassen-setup

# 2. Lesen — was tut das Script? Welche Versionen? Wo braucht es sudo?
less setup-tools.sh
less versions.env

# 3. Ausfuehren
./setup-tools.sh
----

TIP: Auf einem frischen Ubuntu fehlt manchmal `git`. Dann zuerst
`sudo apt-get update && sudo apt-get install -y git` — ein einzelnes,
nachvollziehbares Kommando.

Was fehlt, ohne etwas zu installieren:

[source,bash]
----
./setup-tools.sh --check
----

Danach einmalig:

[source,bash]
----
./setup-identity.sh
----

[cols="1,3",options="header"]
|===
|Werkzeug |Weg

|git, curl, unzip, zsh, gh
|`apt` bzw. `brew`

|JDK, Maven, Gradle

 `JAVA_HOME` wird gesetzt

|Docker (+ compose)
|`apt` bzw. Docker Desktop

|kubectl, minikube
|Release-Binary passend zu System und Architektur

|`brew --cask` bzw. Download von Hand

|powerlevel10k
|`git clone`

|asciidoctor
|gar nicht — laeuft containerisiert, Docker genuegt
|===

== Idempotenz

Der erste Lauf dauert ueber eine Viertelstunde und fuehrt durch ein Dutzend
Fehlerquellen: Netzausfall, `apt`-Lock, abgebrochener Download. Er *wird*
irgendwann abbrechen. Jeder Schritt prueft deshalb zuerst, ob das Werkzeug
schon da ist; ein erneuter Lauf setzt fort, statt Schaden anzurichten.

Derselbe Begriff begegnet euch bei Docker und Kubernetes wieder — dort heisst
das gewuenschte Ergebnis ebenfalls: derselbe Endzustand, egal wie oft
ausgefuehrt.

Ein einzelner Fehlschlag beendet den Lauf *nicht*. Er wird gemerkt, die
uebrigen Schritte laufen weiter, und am Ende steht unter `== Bilanz`, was offen
blieb. Der Rueckgabewert ist dann ungleich 0 — andernfalls waere „ist
durchgelaufen" keine Aussage. Schritte, fuer die es keinen Paketweg gibt,
erscheinen als `[manuell]` und nicht als `[install]`.

`--check` endet mit 0, wenn nichts fehlt, sonst mit 1. Damit laesst sich der
Zustand eines Geraets auch maschinell pruefen.

== Voraussetzungen am Geraet

* RAM >= 8 GB (16 GB empfohlen)
* Freie Partition >= 100 GB fuer Ubuntu
* Virtualisierung im BIOS aktiviert
* BitLocker-Recovery-Key *vorher* gesichert
* Windows-Schnellstart deaktiviert, SATA-Modus auf AHCI

WARNING: Diese Liste vollstaendig abarbeiten, *bevor* die Partitionstabelle
angefasst wird. Jeder Punkt kostet jetzt Minuten und nachher einen Nachmittag;
der Recovery-Key laesst sich hinterher gar nicht mehr beschaffen.

== Versionen und Schuljahre

`versions.env` haelt die verbindlichen Versionen. Je Schuljahr wird ein
git-Tag gesetzt, damit ein Stand nachtraeglich rekonstruierbar bleibt: Faellt
ein Fehler nur bei einzelnen Schuelern auf, ist die verbindliche Version an
*einer* Stelle nachlesbar.

== Zugangsdaten

Keine im Repository. `setup-identity.sh` erzeugt den SSH-Schluessel lokal; der
private Teil verlaesst das Geraet nicht, weitergegeben wird nur `*.pub`.
